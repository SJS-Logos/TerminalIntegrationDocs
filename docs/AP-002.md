# 1. Introduction

This AP defines the physical structure of a service that realizes the logical architecture defined in AP-001 [3].

AP-001 defines architectural invariants — the logical areas (Application, Domain, Shared Kernel, and Capabilities) and the direction in which dependencies must flow. It deliberately says nothing about projects, folders, or assemblies.

This AP supplies that missing layer. It specifies how the logical areas of AP-001 are organized into concrete units of compilation, how those units may reference one another, and how they are named. Where AP-001 asks *what a service is*, this AP answers *how the core of a service is arranged*.

This AP covers only the terms AP-001 introduces: the Application, the Domain, the Domain's Capabilities, and the generic notion of an Implementation. It does not define how Implementations are structured internally; that is deferred to a later AP (Section 9).

This AP is language-neutral in its normative rules. Each rule is expressed in terms of abstract structural units. Examples use a single, language-neutral notation; casing and naming differences between languages are governed by the rule in Section 6.1 rather than by parallel examples.

## 1.1 Structure Does Not Imply Deployment

The structure defined in this AP — separate Units for Domain, Application, and various Implementation concerns — describes **logical boundaries**, not deployment topology.

Multiple separate Units MAY be:
- Deployed as a single process
- Deployed as independent processes
- Combined in any configuration that serves operational needs

The separation into Units ensures modularity, testability, and technology independence (AP-001 §4.1). It does not mandate distributed deployment. Deployment decisions are optimizations made when operational requirements justify the overhead.

# 3. Terminology

This section defines the physical terms used throughout this AP. Logical terms (Application, Domain, Capability, Core, Implementation) retain the meanings defined in AP-001 [3].

**Solution**: The complete set of units that together constitute a single service, together with the metadata that describes how they are built.

**Unit**: The smallest independently compiled artifact. A Unit realizes exactly one logical area of AP-001. In C# a Unit is a project (assembly); in C++ a Unit is a library target.

**Module**: A named grouping of related types within a Unit, corresponding to a folder or namespace. Modules organize a Unit internally; they are not independently deployable.

**Host Unit**: See AP-003 [4].

**Adapter**: See AP-007 [5].

# 4. Logical-to-Physical Mapping

Each logical area defined in AP-001 SHALL be realized by a physical Unit according to the following mapping.

| AP-001 logical area | Physical realization (Unit)                     | Notes                                                                                                                                                                |
| ------------------- | ----------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Domain              | `Core/Domain/` folder                           | Business rules, Entities, and Domain Services within the Core Unit.                                                                                                  |
| Capabilities        | `Core/Capabilities/` folder                     | Domain-owned abstractions at same level as Domain and `SharedKernel/` (see Section 5.1).                                                                             |
| Application         | `Core/Application/` folder                      | Use cases and Contract Models within the Core Unit (see AP-001).                                                                                                     |
| Shared Kernel       | `Core/SharedKernel/` folder                     | Shared immutable business datatypes used across the Core (see Section 5.1.2).                                                                                        |
| Implementation      | Host Units, Deployment Units, and Adapter Units | Incoming implementations are realized in Host Units and composed by Deployment Units (AP-003); technology adapters are realized in dedicated Adapter Units (AP-007). |

## 4.1 Rationale: Why These Four Peer Folders

The Core is divided into exactly four peer folders. This section is informative; it records why the split is drawn where it is.

The split follows a single organizing principle: **each folder isolates concerns that change for a different reason and that depend in a single direction.** AP-001 defines only three logical areas (Application, Domain, Capabilities). The four folders realize those three areas plus one supporting peer, chosen as follows.

- **`Domain/`** holds the business rules — the reason the service exists. It is the innermost concern and depends on nothing outside the Core. It is a peer, not a parent, so that its rules are not entangled with orchestration or transport.  
- **`Application/`** holds use cases and Contract Models — the orchestration of Domain rules for a specific purpose. It changes when workflows change, independently of the rules themselves, and so is kept separate from `Domain/`.  
- **`Capabilities/`** holds domain-owned abstractions (interfaces the Domain and Application need but do not implement). It is a peer of `Domain/` rather than nested inside it to make explicit that these are contracts defined by domain needs, not implementation details, and that both `Domain/` and `Application/` may depend on them (Section 5.1.3).  
- **`SharedKernel/`** holds immutable business datatypes shared across the other three. It is promoted to a peer — rather than being placed inside any one folder — precisely because more than one folder needs it. Nesting it inside `Domain/` would force `Capabilities/` or `Application/` to reach into the Domain for a value type, introducing the awkward or bidirectional dependencies that Section 5.1.2 exists to prevent.

The four are peers rather than a nested hierarchy because their permitted dependencies flow in one direction (Section 7) without any folder containing another. A nested layout would imply ownership relationships that the dependency rules deliberately do not grant.

The count is deliberately small. Additional Core-level folders are not introduced for concerns that belong to Implementations (which live in Host Units, per AP-003) or to cross-cutting utilities (such as the pre-AP shared `Core` folder documented in Background-LegacyFolderMigration). Keeping the Core to these four peers preserves the property that the Core is verifiable without any Implementation and without deployment (Section 8).

On naming: each folder is named for the concept it realizes in AP-001's ubiquitous language rather than for a technology or a layer number. Three of the four names are drawn directly from established literature and need no new justification:

- **`Domain/`** realizes the **Domain Model** [8] — the layer Evans defines as holding the business concepts, rules, and state that are the reason the software exists.  
- **`Application/`** realizes the **Application Layer** [8] — Evans's thin layer that directs work by coordinating the Domain Model, holding no business rules of its own.  
- **`SharedKernel/`** retains Evans's **Shared Kernel** [8] name, the explicitly shared subset of the model that multiple parts agree to keep consistent, to avoid inventing a synonym for a well-understood concept.

The fourth name, **`Capabilities/`**, is the only term this AP does not inherit verbatim from Evans. Its conceptual grounding — as the driven (secondary) ports of Hexagonal Architecture applying the Dependency Inversion Principle — is established in AP-001 §6.5 [3] and is not restated here. This AP is concerned only with realizing that logical area as a peer folder. "Capabilities" is preferred over the bare word "Ports" because it names the folder for what the domain requires (the capabilities it needs from the outside world) in the ubiquitous language of the service, rather than for the structural metaphor; the two terms are synonymous for the purposes of this AP.

# 5. Unit Layout

A service SHALL be organized into the Units described in this section. Examples use a language-neutral notation.

The prefix `MyPaymentService` represents the service name; the actual name is derived from the application or bounded context being implemented (e.g., `MyPaymentService`, `MyLoyaltyService`, `MyOrderingService`). Each language applies its own casing convention per Section 6.1.

## 5.1 The Core Unit

The Core Unit realizes the Domain, Capabilities, and Application of AP-001 as a single compiled Unit. It is organized into four peer folders:

The Core Unit MUST NOT reference any external Unit.

```text
Core/
├── Domain/
│   ├── Entities/
│   └── Services/
├── SharedKernel/
│   ├── Money/
│   ├── Identifiers/
│   └── Dates/
├── Capabilities/
│   ├── Persistence/
│   ├── Messaging/
│   └── ExternalServices/
└── Application/
	├── UseCases/
	└── Contracts/
```

### 5.1.1 Domain Folder

The Domain folder contains business rules, Entities, and Domain Services.

The Domain folder MAY reference `SharedKernel/` and `Capabilities/`, but MUST NOT reference the `Application/` folder or any external Unit.

### 5.1.2 SharedKernel Folder

The `SharedKernel/` folder contains shared immutable business datatypes that form part of the service's ubiquitous language.

`SharedKernel/` exists as a top-level peer folder so that Domain, Capabilities, and Application can share the same business datatypes without introducing awkward bidirectional dependencies or duplicate transport-neutral models.

The SharedKernel folder MUST NOT reference Domain, Capabilities, Application, or any external Unit.

### 5.1.3 Capabilities Folder

The `Capabilities/` folder contains domain-owned interface definitions that external adapters must implement. These interfaces are the driven (secondary) ports of the Domain; their conceptual grounding in Hexagonal Architecture and the Dependency Inversion Principle is established in AP-001 §6.5 [3]. It is at the same level as Domain to emphasize that:
- Capabilities are contracts defined by domain needs
- Capabilities are independent abstractions, not implementation details
- Both Domain and Application can reference these abstractions
- Capabilities MAY use `SharedKernel/` directly in their contracts when that preserves the ubiquitous language of the service

Capabilities contains only interface definitions and data contracts, no implementations.

The Capabilities folder MAY reference `SharedKernel/`, but MUST NOT reference `Domain/`, `Application/`, or any external Unit.

### 5.1.4 Application Folder

The Application folder contains use cases and Contract Models (inputs, outputs, and messages). Application MAY reference `Domain/`, `SharedKernel/`, and `Capabilities/`, but MUST NOT reference any external Unit.

## 5.2 Host Units (Incoming Implementations)

Host Units realize incoming implementations and are defined in detail in **AP-003: Incoming Implementations**.

Each inbound transport (HTTP, MassTransit consumers, gRPC, etc.) has its own dedicated Host Unit that contains:
- Transport-specific endpoint classes
- Transport-to-Application mappings
- Host configuration registration callable from deployment composition

A Host Unit SHALL be implemented for exactly one Core Unit.

Pure Host Units are library-style and do not define standalone process entry points.

For complete specification of Host Unit structure, naming, organization, and composition/deployment separation, see AP-003.

# 6. Naming Conventions

Unit names SHALL be derived from the logical area they realize.

* The Core Unit SHALL be named to identify the service/bounded context following the pattern `ServiceName.Core` (e.g., `MyPaymentService.Core`, `MyLoyaltyService.Core`, `MyOrderingService.Core`). The `My` prefix in these examples is a placeholder only; a real name SHALL substitute a scope (see below).
* A service name SHALL encode the scope it operates in — the vendor, bounded context, or capability that distinguishes it from other services (e.g., `StripePaymentService` rather than a bare `PaymentService`). This AP does not mandate a particular scope vocabulary; it requires only that the scope be explicit in the name.
* Host Units SHALL follow the pattern `ServiceName.HostType` (e.g., `MyPaymentService.HttpHost`, `MyPaymentService.MasstransitHost`). See AP-003 for details.
* Deployment Units (including Composition Units) SHOULD use deployable-role suffixes such as `Api`, `Worker`, `Migrator`, or `AppHost` (e.g., `MyPaymentService.Api`, `MyPaymentService.Worker`). See AP-003 for details.
* A service SHALL adopt a single casing convention and apply it consistently to all Unit and Module names. This AP does not mandate a particular casing.
* Where a language has an established convention, that convention SHOULD be followed: in C# the logical name is used directly (for example `MyPaymentService.Core`, with the root namespace matching); in C++ the same name SHOULD be mapped deterministically to the project's chosen convention — commonly the lower-cased, delimiter-normalized `snake_case` form (for example `mypaymentservice_core`) following standard-library precedent.

The illustrative names in Section 5 use the logical form. The mapping to a language-specific form SHALL be deterministic, so that a Unit's identity is recognizable across languages.

# 7. Reference Rules

Unit references SHALL enforce the Dependency Rule of AP-001: dependencies move toward business meaning, and the Core depends upon nothing outside itself.

Within the Core Unit, the following internal reference directions are permitted:

```text
Application/ ──▶ Domain/
Application/ ──▶ SharedKernel/
Application/ ──▶ Capabilities/
Domain/ ──▶ SharedKernel/
Domain/ ──▶ Capabilities/         (Domain may reference its own capability interfaces)
Capabilities/ ──▶ SharedKernel/   (Capabilities may use shared business datatypes in their contracts)
```

The following references are prohibited:

* `SharedKernel/` to `Domain/`, `Capabilities/`, or `Application/`.
* `Capabilities/` to `Domain/` or `Application/`.
* `Domain/` to `Application/` (within Core).
* Core Unit to any Host Unit.

A Host Unit MUST reference exactly one Core Unit (through that Core's Application layer). The Core Unit MUST NOT reference any Host Unit.

Deployment Units MAY compose multiple Host Units and, by composition, may deploy functionality from multiple Core Units in one process.

These rules SHALL be enforced by the build system, expressed as follows in each language.

**C#** — enforcement is by project reference and namespace organization. The Core is a single project. Folder-level dependencies within the Core (Domain/ vs SharedKernel/ vs Capabilities/ vs Application/) are enforced by namespace visibility and code review. The Core project declares no project references to Host projects. Each Host project SHOULD reference exactly one Core project; Deployment projects MAY reference multiple Host/Core projects as needed for composition.

**C++** — enforcement is by target dependency and header visibility. The Core is a single library target. Folder-level dependencies are enforced by include path discipline and header guards. The Core target declares no dependencies on Host targets. Each Host target SHOULD depend on exactly one Core target; Deployment targets MAY depend on multiple Host/Core targets as needed for composition.

# 8. Testing Structure

The physical structure SHALL support the testability required by AP-001 [3].

* The Core Unit (containing `Domain/`, `SharedKernel/`, `Capabilities/`, and `Application/` folders) SHALL be verifiable by tests that reference only the Core Unit, without any Implementation and without deployment.
* Test Units SHALL follow the same reference rules: tests MAY reference the Core Unit and exercise its public API, but the Core MUST NOT reference test Units.

As a suggested organization, test projects SHOULD follow the same Unit structure as production code and be separated by test category. For example:

```text
MyPaymentService.Core/
MyPaymentService.Core.UnitTests/

MyPaymentService.Infrastructure.Sql/
MyPaymentService.Infrastructure.Sql.IntegrationTests/

MyPaymentService.HttpHost/
MyPaymentService.HttpHost.IntegrationTests/

MyPaymentService.EndToEndTests/
```

This suggestion is intended to preserve traceability between production Units and their tests while keeping test categories explicit. Unit tests typically align to Core Units, integration tests to technology-specific Units, and end-to-end tests to the fully composed service.

This structure is consistent with the test pyramid [7].

---

# 9. Scope and Evolution

This AP defines the structure of the Core: a single Core Unit organized into four peer folders (`Domain/`, `SharedKernel/`, `Capabilities/`, and `Application/`).

Host Units (incoming implementations) are defined in AP-003. The internal structure of transport-specific endpoints, mappings, how Hosts organize composition, and how configuration is managed are all specified in AP-003.

---

# 10. Compliance

A service complies with this AP if:

* The Core is realized as a single Unit organized into `Domain/`, `SharedKernel/`, `Capabilities/`, and `Application/` peer folders (Section 5.1).
* `SharedKernel/` is a peer folder at the same level as Domain, Capabilities, and Application, and contains shared immutable business datatypes (Section 5.1.2).
* Capabilities is a peer folder at the same level as Domain, SharedKernel, and Application, and MAY reference `SharedKernel/` while remaining free of implementations and external dependencies (Section 5.1.3).
* Host Units (incoming implementations) are structured according to AP-003.
* No retired legacy name is used as a canonical role name.
* Internal Core folder references satisfy the dependency direction defined in Section 7.
* The Core Unit is verifiable without any Host Unit and without deployment.
